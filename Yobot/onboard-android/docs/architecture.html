02 / Concurrency

Several loops. One future state owner.

Execution lanes are distinct from modules. A coroutine is not a dedicated thread; the current Brain scope is not a sequential Executive.

Android main threadLifecycle + recognizer + Compose
Activity start / stop→Hearing callbacksUI + frame clock

Hearing marshals operations with a main Handler. Compose launches concurrent animation coroutines; they are not separate sensor threads.

HandlerThread("imu")Requested game rate ≈ 50 Hz
Latest sensor values→BodyMotion StateFlowMotionClassifier → callback

Each linear-acceleration reading publishes with cached gravity / gyro. Classification happens here; the callback runs here too.

Dispatchers.IOShared coroutine pool
Batch dispatcher→One worker per sinkDrop reporting

Telemetry explicitly overrides Brain’s Default dispatcher. Bounded queues isolate sinks; overflow drops data instead of waiting for I/O.

TCP threadsAccept + per-client reader / writer
Accept connection→Client line queue→Socket writer

Slow clients lose new lines when their queue is full. Reader threads detect disconnects. Default telemetry port: 7777.

Executive laneRequired by design · not implemented
Queued ExecutiveEvent→step(state, event, time)→State + effects

One single-threaded owner processes events sequentially. Queue, dispatcher, cancellation, and effect runner still need implementation.

Two different delivery guarantees: StateFlow exposes the latest value; the face can skip intermediate IMU samples. Telemetry uses bounded, lossy queues. Neither is the future Executive’s decision inbox.

03 / Ownership

Brain assembles. Executive will decide.

What Brain.kt actually owns today

YobotApplication.onCreate() constructs one Brain for the application process. Brain is the composition root: the place where concrete objects and their connections are assembled.

  1. Creates telemetry, its three sinks, face, hearing, IMU, and the unconfigured inference seam.
  2. Starts telemetry and TCP serving immediately; emits a boot event listing imu→face.
  3. Starts / stops senses when requested by MainActivity. Each sense handles repeated starts.
  4. Receives percepts on the caller’s thread. Drops partial speech from this route; serializes final speech and motion into telemetry.
  5. Exposes faceMotionReflex = imu so the renderer can read motion directly.

It owns no RobotState, does not select expressions, schedule thinking, run skills, or serialize decisions. Its SupervisorJob + Dispatchers.Default scope is infrastructure.

app / Brain.kt ↗

Where the Executive belongs

The contract already lives in :core / executive, alongside events, state, and policy contracts. Brain would construct and connect an implementation; Brain’s identity as the composition root can stay intact.

sense / feedback / command → Executive.post(event) → sequential ExecutiveLogic.step(...) → Step(newState, effects) → effect runner → outputs / cognition ← completion events back to Executive

This is the intended placement, not existing runtime wiring. An event-loop implementation and an effect runner are still missing. Long work must run outside the state-owning loop and return as events.

RobotState currently contains only FaceState. Cognition, validated bounded skills, richer state, and a real inference backend remain to be built. The model must not command servo angles.

05 / Questions that matter

Reading the seams correctly

Does every sense drive an output?

No. Final speech and classified motion currently end at telemetry. Speech partials stay visible through HearingStatus but Brain filters them out of percept telemetry. No hearing-to-mouth connection exists. The sole declared reflex is IMU → face, exposed through Brain and passed by MainActivity.

How do BodyMotion, MotionReflex, MotionClassifier, and FaceMotion differ?

BodyMotion.kt is the shared sensor sample: gravity and linear acceleration in m/s², rotation rates in rad/s, and derived roll/pitch in degrees. MotionReflex.kt is the presentation access contract exposing the latest sample as StateFlow<BodyMotion>. MotionClassifier.kt converts samples into coarse Motion percepts on the IMU thread. FaceMotion.kt is the renderer-side animation model that consumes samples. Separating the data and reflex files changes package ownership, not concurrency or wiring.

Does the face’s motion change RobotState or FaceState?

No. The renderer combines its sustained FaceState target with the latest BodyMotion and ambient animation. The reflex changes presentation, not decisions, thinking, or actuators. The default target stays Idle until a future caller sets another target. ComposeFace.react() is a transport scaffold with no renderer consumer.

What happens when the activity stops?

MainActivity calls Brain.stopSenses(). Hearing posts cleanup to the main thread; IMU unregisters sensors, quits its HandlerThread, and resets BodyMotion to the resting default. Telemetry continues for the process lifetime. Sensor lifecycle and telemetry lifecycle are deliberately different.

What still needs a concurrency decision?

The Executive contract says post(event) but supplies no queue. Implementing it must define inbox capacity, ordering across concurrent producers, overload behavior, single-thread ownership, stale thought results, cancellation, and shutdown. RequestId and UtteranceId exist for correlation, but the policies using them do not. The proposed graph shows roles, not a finalized scheduler.

Where do locomotion and Pico safety fit?

Locomotion is not connected in this Android tree. Project guidance places model requests at the bounded-skill level and reserves servo timeout, stop, and watchdog behavior for MicroPython on the Pico. The current presentation-only reflex must not be repurposed into actuator control without revisiting the design. The future IMU input to a locomotion policy is explicitly still an open question.
